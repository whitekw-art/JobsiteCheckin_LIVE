- **`fix/2026-08-27-google-connection-integrity`** — **LIVE ON PRODUCTION 2026-08-27.** Merged into `dev` via PR #222 (commit `704f585`), then promoted to `main` via PR #223 (merge commit `1e37147`) in the same push that shipped GBP auto-posting itself. Fixes two independent bugs in the shared Google OAuth layer between GSC and GBP, found when Keith live-tested GBP auto-posting on staging: publishing errored, and only reconnecting GBP fixed it. **Confirmed working on staging by Keith before promotion** — disconnect/reconnect combinations tested across both integrations. Design doc: `docs/plans/2026-08-27-google-connection-integrity-design.md`.
  - **Bug A — disconnecting one Google integration silently revoked the other.** GSC and GBP share ONE OAuth client, and both consent URLs set `include_granted_scopes: true`, merging their scopes into one combined authorization on the customer's Google account. Per Google's own OAuth docs, revoking a token representing a combined authorization revokes every scope in it at once. Both `DELETE` handlers revoked unconditionally, so disconnecting either integration killed the other's access while its own database row still read `'connected'`. **Fix:** each `DELETE` now checks whether the sibling integration still holds a refresh token before calling `revokeAccess()` — skip the Google revoke when it does, clear only local credentials. The grant is still fully revoked when the customer disconnects both, just on the second disconnect rather than the first. Verified against the full state matrix with an 18-case logic suite (`node` script, not committed — all combinations of connected/disconnected × disconnect-GSC/disconnect-GBP × sequential-both), all pass.
  - **Bug B — a dead connection kept rendering as Active, independent of Bug A.** Both `lib/gbpApi.ts` and `lib/gscApi.ts` already had a `classify()` function that correctly detected a revoked grant (401/403 → `needsReconnect: true`), but the signal died in a log line: never written to `gbpConnectionStatus`/`gscConnectionStatus`, never read by the dashboard, only console-logged by the auto-post background hook. This is what made Bug A invisible, and it is independently reachable whenever a customer revokes ProjectCheckin from their own Google Account permissions page, or a grant simply expires. **Fix:** persist a new `'needs_reconnect'` value to both status columns (no migration — both are already nullable `String?`). It composes automatically with every existing gate, since all of them check equality against `'connected'`: the API's `connected` flag flips false, `gbpSync`'s post/retract functions refuse to run (stopping a retry storm against a dead grant on their own), and the Reporting GSC section reverts to its not-connected copy — zero of those four call sites needed a code change. The one place it did NOT compose cleanly: both Connections cards fell through an unrecognized status to the plain "Connect" state, telling the customer nothing about why their working connection vanished — that's the exact failure Keith hit. Both cards (`app/account/page.tsx`) got an explicit `'needs_reconnect'` branch: a red status dot labeled "Reconnect needed," a one-line explanation, and a Reconnect button. The dashboard (`app/dashboard/page.tsx`) now reads the gbp-post route's HTTP 409 and shows a "Reconnect Google" link next to the error instead of implying a retry will work.
  - **Also narrowed `classify()` in both modules from `401 || 403` to 401 only.** Treating 403 as "needs reconnect" was harmless when it only produced a log line; now that it flips a customer-visible card, a quota-exhaustion 403 (a real, distinct condition Google also returns as 403) would have told a working customer to reconnect for no reason. 403 now falls through to a plain retryable error with its own log line, pending real evidence a revoked grant ever returns 403 on these specific endpoints.

## POTENTIAL NEW FEATURE — Zapier/Make Integration + Automated Social Media Posting (2026-07-21)

**Status:** Idea stage only, not scoped, not started. Keith is especially interested in the social-media-auto-posting angle specifically and wants to explore it further.

### Origin
Surfaced while doing an exhaustive "is there anything better than our current widget/CNAME/API-plugin/RSS roadmap" pass, specifically for customers whose site can't be reached by native CMS integrations (e.g. static AI-coded sites like keith-white.com). Zapier/Make came up as a genuinely new, previously-unconsidered option — not a replacement for the existing five-option roadmap, but a complementary distribution layer.

### The Zapier/Make idea itself
Build one Zapier "app" (or Make equivalent) exposing a "New Job Published" trigger. Lets any customer with their own Zapier/Make account connect ProjectCheckin to literally any of Zapier's 9,000+ supported apps — WordPress, Notion, Google Sheets, social platforms, anything — without ProjectCheckin building/maintaining a native integration per destination.
- **Real precedent:** CompanyCam (direct trade-tech competitor) already ships a Zapier integration — this is a validated pattern in this exact market, not a novel/risky bet.
- **Cost to build:** moderate one-time engineering (a Zapier "app" following their standard trigger/action framework, well-documented path).
- **Limitation:** requires the customer to have and pay for their own Zapier/Make account and build their own automation — real friction for a non-technical small/medium-business ICP. Best positioned as an option for power users, not the primary mechanism for a flagship feature like social posting.

### Automated social media posting — the part Keith is most excited about
Three real approaches researched and compared (2026-07-21), not just Zapier:

1. **Zapier/Make** (above) — works, but customer-dependent setup, doesn't feel native.
2. **Direct Meta Graph API integration** (build and own it fully in-app) — feels fully native, no third-party dependency, but Meta requires **formal app review taking 2-4 weeks per submission** (separate reviews for `instagram_business_basic` and `instagram_business_content_publish`, each needs a screencast showing the full user connection/posting flow), plus Business Verification for full access. Customer's Instagram must already be a Business/Creator account linked to a Facebook Page — a personal Instagram account cannot be used. **This is the same category of friction/timeline as the GBP API application already in progress** — familiar process, not a new unknown.
3. **Unified social media API middleman** (integrate once, customers connect accounts through ProjectCheckin's own UI — feels fully native, no separate paid account needed on the customer's end):
   - **Ayrshare** — 13 platforms including Facebook, Instagram, LinkedIn, TikTok, X, and Google Business Profile. Real product, API-first, built for exactly this use case. **Pricing scales badly for a B2C SaaS with many customers** — roughly $770/month at 50 connected profiles (per-profile billing model).
   - **Postiz** — open-source, self-hostable for free, or cloud starting ~$99/month for 50 accounts / 400 posts. Supports 30+ platforms, the most of any option checked. **Meaningfully cheaper at scale than Ayrshare** — self-hosting removes the recurring vendor cost entirely at the expense of more DevOps/maintenance burden on ProjectCheckin's side.

**Current lean (not decided):** for social posting specifically, option 3 (especially Postiz) looks like the stronger fit — native feel, contained/predictable cost, doesn't push setup burden onto the customer. Zapier/Make remains valuable as a separate, complementary long-tail connector for whatever isn't natively built (any CMS, any tool), not as the primary social-posting mechanism.

### Why this matters
Automated social posting would be a strong Titan-tier value-add on top of the existing GBP posting feature — same underlying job/photo data, one more high-visibility distribution channel, directly serves the north star (more customers for the service business) by putting finished work in front of people where they already look.
